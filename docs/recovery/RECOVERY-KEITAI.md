# KYF37 keitai recovery (TWRP engine, cursor-less D-pad UI)

Status 2026-10-09: built, signed, verified on the host (including the real TWRP binary running under qemu-arm with a
fake framebuffer). **Not flashed, not booted on the phone.** The lead runs the boot-slot test with the owner present.

## Design decision
TWRP's backend (partitions, zip installer/update-binary, nandroid backup/restore, adbd, `twrp` CLI/OpenRecoveryScript) is
unchanged. The GUI engine got a new object, **`<keymenu>`** (`device-inspection/keitai-recovery/gui/keymenu.cpp`, a subclass
of the stock `GUIListBox`), and a **new XML theme** generated by `device-inspection/keitai-recovery/build-keitai-theme.py`.
Rejected: a separate minui process driving `twrp` (would re-implement progress/console/backup-state plumbing and add a second
process that must not fight the GUI for the framebuffer/input; the CLI path stays available anyway). Theme-only XML was not
enough because stock TWRP has no keyboard focus. The mouse cursor and touch emulation of the previous port are disabled
by `TW_KYF37_KEITAI` (set in BoardConfig by `apply-keitai-recovery.py`).

## Key map
| Key | Action |
|---|---|
| Up / Down | move highlight (wraps) |
| OK (center, Enter) | activate highlighted row (acts on key release) |
| 1-9, 0 | jump to and activate the row showing that number |
| Left / Right | page up / down in menus, browsers, viewers; scroll the install/backup log on running/finished screens |
| `*` / `#` | first / last row |
| Clear (355) or F2 | Back (inside a folder browser: up one folder first) |
| F1 or End/Power | main menu |
| Side key (254) | screenshot to SD (stock TWRP `screenshot`) |

Footer on every screen shows `F1 Menu | OK Select | Back (Clear)`. Highlight is an amber bar with a left marker.

## Screens
Main: 1 Install zip, 2 Backup, 3 Restore, 4 Wipe/Format, 5 Mount/Unmount, 6 File browser, 7 Logs (recovery log, dmesg, last_kmsg,
copy logs to SD), 8 Reboot/Power off, 9 Tools (ADB sideload, Settings incl. zip-signature toggle and English/Espanol, Extras, key help).
* Install: folder browser on the SD (.zip) -> confirmation (default **Cancel**) -> console + progress -> result screen with
  scrollable log, Back / Main menu / Reboot system / Wipe cache+dalvik. `Back` is disabled while a zip runs.
* Backup: tick boot/system/data, choose SD or internal target, "Start backup" (key 9); progress + log; Restore: pick source,
  pick backup folder (newest first), tick partitions, "Restore selected..." (two-step) or "Delete this backup..." (two-step).
* Wipe: cache+dalvik (one confirm), factory reset, format data, advanced (dalvik/cache/system/data) - the last three are
  **two-step**: step 1 default row = Cancel, "Continue"; step 2 "FINAL CHECK": default Cancel, the confirm row only accepts the
  **digit key 0** (OK on it does nothing). Modem/persist/keystore/misc/recovery partitions are never offered anywhere.
* `adb shell` (root), `adb push/pull`, `adb shell twrp install|reboot|mount|...` do not depend on the GUI (adbd is started by
  `init.recovery.qcom.rc`; the `twrp` CLI talks to the same ORS fifo). The recovery still shows the "keep /system read-only"
  page first (as stock did); press 1 (or send the CLI command, the page keeps processing it).

## Extension point ("Something else")
`EXTRAS` in `build-keitai-theme.py` (list of `(label, [actions], danger)`) adds rows to Tools > Extras; re-run the script,
`apply-keitai-recovery.py`, build. Zero-rebuild alternative: drop `*.sh` files into `/external_sd/keitai-extras/`; Extras > "Run a
script from SD card" lists them and runs the chosen one as root after a two-step confirm (output in the console).
New object types/modes go in `keymenu.cpp` (static menu, folder browser, text viewer exist).

## Safe test plan (do not run without the owner present)
`tools/keitai-recovery.ps1` is dry-run unless `-Execute`; it holds `phone-lock.ps1`, only writes boot or recovery, hash-gates and reads back.
1. `.\tools\keitai-recovery.ps1 -Action bootslot-install -Execute` (phone in Android, adb root): backs up boot (verified, laptop + SD +
   `/data/local/tmp`), writes the `/boot`-signed keitai image, clears misc, reboots, waits for adb state `recovery`.
2. Walk the checklist on the phone: main menu numbers, Up/Down/OK/Clear, F1, install a small test zip, `adb shell twrp reboot system`
   from the laptop, Backup of /boot to SD, wipe screens (stop at step 2 -> Cancel), file browser, log viewer, reboot menu.
3. `.\tools\keitai-recovery.ps1 -Action bootslot-restore -Execute` (adb works in the keitai recovery): writes the saved Android boot back, clears misc, reboots.
4. Only after 1-3 passed: `New-Item phone-backup\keitai-test\bootslot-passed.flag`, then `-Action recovery-install -Execute`
   (backs up the TWRP currently in recovery, writes, verifies, auto-restores it if the readback fails). Test with `tools\enter-twrp.ps1`.
5. Rollback any time: `-Action recovery-rollback -Execute`.

### If it does not come up
* Boot-slot test: boot partition holds the keitai image. If the screen stays dark but USB shows adb (state `recovery`), run step 3.
  If nothing enumerates: remove battery, use the SD download-mode procedure in `KYF37-USB-RECOVERY-RUNBOOK.md` and
  `device-inspection/kyf37-vendor-recovery.py` to write `phone-backup/keitai-test/boot-android-backup.img` (md5 in `boot-android-backup.md5`)
  back to the boot partition (physical key combos do not reach recovery on this phone). The recovery partition (working TWRP) is untouched
  during the boot-slot test, so `enter-twrp.ps1` still works whenever Android boots.
* After recovery-install the same download-mode procedure restores `recovery-twrp-backup.img`.

## Verified vs not verified
Verified on host: theme XML well-formed and statically checked (two-step rule, no protected partition in UI, all page targets); real TWRP
binary built with the keitai engine loads the theme and renders every tested screen; D-pad/digit/Clear/F1/`*` events injected as raw Linux input
events navigate main, wipe confirm1/confirm2 (OK on Cancel returns), backup setup toggles, reboot menu, log viewer scrolling, folder browser
(descend, `..`, Back-up), install picker + confirmation + signature toggle; image header/signature/ramdisk checks; shipping binary contains no test hooks.
**Not verified:** anything on hardware (real fb pixel format/blanking, real key repeat timing, power/side key behaviour, SD mount), and under
emulation the actual flash, backup, restore, wipe, mount and reboot execution (no partitions exist there). Spanish strings are
machine-written and untested visually. Text entry (backup rename) is intentionally absent. Encrypted data is not supported (stub page).
Long zip names are shrunk to fit (about 60 % size). The first screen after boot is the stock "system read-only" question.
